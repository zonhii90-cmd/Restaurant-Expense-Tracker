# 采购更正、作废与修改记录：操作规格草稿

状态：用户已同意本流程并开始实施；本规格对应代码已实现。上线仍需执行数据库升级，参见[设置与验证说明](purchase-corrections-setup.md)。

## 1. 已确认的目标

- 单店使用，专注采购记录与报表。
- 新采购保存成功后直接进入报表，不增加逐笔审批。
- 员工提出错误，由经理负责更正或作废。
- 保留修改前后内容、操作人、时间和原因。
- 作废采购保留历史，但不计入有效金额、数量及报表合计。
- 员工在网页内提交更正申请，由经理在后台处理。

以下描述本轮实现的行为，不代表线上数据库已完成升级。[当前系统现状](current-system.md)与[业务决策](adr/0001-retain-purchase-change-history.md)仍分别说明现有能力及已确认规则。

## 2. 员工发现错误

用户已选择网页内提交更正申请。具体界面建议如下：

1. 员工在 My purchases 打开自己的 Purchase details。
2. 点击 Request correction，填写错误说明，例如「Cooking Oil 金额应为 RM 50，误填 RM 500」。
3. 点击 Submit request。成功后显示 Pending；采购原值不变，仍按原值计入报表。
4. 经理处理后显示 Corrected、Voided 或 Declined，并可查看处理说明。

建议首版使用文字说明，不让员工直接改动已保存采购，也不自动把申请内容应用到报表。一个采购同一时间保留一个待处理申请；处理后如仍有新错误，可以重新申请。经理看到的申请保留提出时的采购版本，避免把旧申请误用于已更正的资料。

经理后台提供待处理申请列表与数量提示，可进入关联采购查看完整资料并更正、作废或拒绝。外部邮件、WhatsApp 或手机推送不在本轮范围。

## 3. 经理更正采购

建议入口：Management → Purchases → Purchase details → Correct purchase。

1. 显示完整采购，不能只显示当前物品筛选命中的部分行。
2. 显示 Entered by 与 Notes，帮助经理核对原始记录。
3. 允许更正采购日期、供应商、单据编号、备注，以及物品名称、数量、单位、行金额；可增加或移除物品行，但最终仍须包含 1–100 行。
4. 填写必填的 Reason for correction。原始录入员工与录入时间不改变；经理身份作为独立的更正操作人记录。
5. 保存前显示修改前后差异与新合计。
6. 点击 Save correction；服务器确认成功后，才更新明细和报表。

沿用现有数量、金额、物品名称、单位及长度校验。修改采购的供应商或物品时，不能全局改名共享目录而影响其他采购。

建议首版保留原单据照片，不提供替换或删除已保存照片；照片修改需要另外设计历史凭证的保留方式。

无实际内容变化时，不创建一次虚假的更正事件。只有说明而没有资料变化的申请，可通过处理说明结束，不应冒充金额或物品更正。

## 4. 经理作废采购

建议入口：Purchase details → Void purchase。

1. 展示采购日期、供应商、原金额及单据编号。
2. 填写必填的 Reason for voiding。
3. 确认提示：该采购将保留，但不再计入报表。
4. 点击 Void purchase。成功后显示明显的 Voided 状态，保留原物品、金额、照片及修改记录。

建议首版不提供永久删除或恢复作废。作废有误时，保留这笔历史，另录一笔正确采购，并在备注引用原采购；如果需要一键恢复，应先定义恢复权限与审计规则。

作废是状态变化，不应把历史原金额改为零。已有作废采购不能继续更正或重复作废。

## 5. 历史与报表

- Dashboard、Monthly reports、Suppliers 及采购统计只使用有效采购；作废采购不增加金额、数量、采购笔数、供应商数或物品数。
- Purchases 默认显示有效采购；建议状态筛选 Active / Voided / All，员工仍只能查看自己的记录。
- 查看作废历史时，原始金额可见，但必须明确标记不计入统计。All 视图中的有效合计不能把作废金额加回来。
- 更正后重新按采购日期、供应商、物品与单位归类。跨月更正须同时影响原月份及新月份，不能只刷新当前页面金额。
- Excel 的物品和供应商汇总始终排除作废采购。导出作废或全部历史时，明细须含状态，避免把作废明细误认为有效合计。
- 更正申请尚未处理时不改变采购值或报表；不把更正申请变成逐笔采购审批。

## 6. 修改记录

建议在每笔 Purchase details 中加入 Change history，记录：

| 内容 | 要求 |
| --- | --- |
| 操作类型 | Corrected / Voided；网页申请方案另记 Requested / Declined / Resolved |
| 操作人 | 服务器确认的账号身份及当时显示名称，不由浏览器任意指定 |
| 时间 | 服务器时间，界面以马来西亚时间显示 |
| 原因 | 必填；不能只记「修改过」 |
| 修改前后 | 采购头、完整物品行、有效状态及对应金额；不能只保留新的合计 |
| 原始关联 | 原采购、原录入人以及适用时的更正申请 |

记录不能经普通浏览器操作编辑或删除。经理可看全店记录，员工只看自己采购相关记录，不开放其他员工身份或全店账号目录。Login history 仍独立保留，不代替 Change history。

## 7. 权限、保存及并发

当前数据库允许员工通过 API 修改或删除自己的采购。因此，增加按钮前必须同时收紧底层写入规则，不能只隐藏员工的编辑按钮。

- 新增采购继续允许有效员工提交，且 created_by 必须是本人。
- 已保存采购只能由有效经理通过受控操作更正或作废；普通客户端不能绕过操作直接改头、物品行或状态，也不能删除采购或伪造历史。
- 采购更新与修改记录必须同一事务提交；如果某一行不合法或审计写入失败，全部回滚。
- 两名经理同时处理同一采购时，较旧版本保存必须失败并要求重新载入；不得静默覆盖另一名经理的结果。
- 同一操作网络重试不能重复更正、作废或插入历史；重复请求使用稳定操作标识校验一致性。
- 新增采购的旧重试请求，在采购已更正或作废后，不能把资料覆盖回初次录入值、复活采购或重复插入物品。
- 原照片保持私有；查询作废历史时仍可按原权限查看凭证，不能因为报表过滤作废而误断照片访问权限。
- 读取失败或服务器结果不确定时不得显示成功；保留草稿并提示刷新核对，避免重复操作。

## 8. 手机界面

界面保持英文，品牌使用 #ec6608、黑与白。更正表单用单列布局、至少 16px 输入文字及易点按按钮；表单主要按钮为 Save correction。作废作为独立危险操作，并清楚说明结果，不能与保存按钮混淆。

更正期间离开页面须提示未保存内容；保存过程中防止重复提交。Change history 在手机使用可展开卡片呈现差异，避免必须横向滚动才能看懂。

## 9. 验收示例

1. 员工输入 RM 500，经理改为 RM 50：采购保留同一个身份及原录入人；报表仅计 RM 50；历史可查 RM 500 → RM 50、经理、时间与原因。
2. 经理把采购日期从十月改为十一月：十月扣除，十一月增加；Excel 与界面一致。
3. 更正一笔含三个物品的采购，即使从 Cooking Oil 搜索结果进入，也必须编辑完整三行；不能误删未命中的物品。
4. 作废一笔含 2 tin、RM 180 的采购：有效数量、金额与笔数均扣除；历史仍保留 2 tin、RM 180 及原照片。
5. 员工直接调用数据库 API 更新／删除已保存采购或写入修改记录：拒绝；员工正常新增采购仍成功。
6. 两位经理读取同一版本，第一位保存后，第二位旧版本提交失败；第一位结果与历史不被覆盖。
7. 修改中某一物品数量为零：整个更正失败，旧数据与有效报表不变，不产生成功历史。
8. 保存响应丢失后重试：只产生一次操作；原采购保存重试不撤销更正或作废。
9. 账号停用后即使仍持有登录令牌，也不能提交申请、更正、作废或读取受保护历史。
10. 若采用网页内申请：员工只能对自己的有效采购提交，经理可处理；申请被拒绝或尚未处理时金额保持原值，处理完成后不能被旧申请再次覆盖。

## 10. 上线与范围

实施需新增数据库升级、权限与历史存储、查询和报表过滤，以及网页操作。仓库文件更新不会自动升级线上 Supabase；迁移前应核对现有配置与备份，并以真实员工／经理账号验证。

本地 PostgreSQL 权限、事务、并发及重试测试与浏览器流程测试都需要覆盖；线上真实账号、私有照片及手机验证须另行完成。没有完成升级时，应显示明确的功能未就绪提示，而非忽略状态或假装保存成功。

此轮不增加多店、库存结余、付款管理、自动识别、照片替换、全局目录合并或外部消息推送。本轮保留原照片、不恢复作废采购、不永久删除，均已作为首版边界实现。
