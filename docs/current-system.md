# Stocklog 系统现状与业务梳理

整理日期：2026-10-28（马来西亚时间）。这是现有系统的说明和本轮讨论记录，不是已批准的新功能开发计划。界面文字继续以英文为主。

本轮开发更新：采购更正、作废及历史记录已在代码中实现，线上需先执行[数据库升级](purchase-corrections-setup.md)才可使用。以下原始盘点及业务确认记录保留作背景；其「尚未实现」描述以本说明为更新依据。

## 一、系统用途

目前的 Stocklog 是餐厅采购记录系统：员工输入采购，管理者查看明细、每月数量与金额，并导出 Excel。金额使用 MYR，日期按马来西亚时间处理。

现在记录的是「买进了什么、买了多少、金额多少」，不计算实际剩余库存、食材消耗、付款进度或餐厅利润。当前数据结构没有分店字段，也没有不同餐厅之间的资料隔离。

## 二、人员与入口

| 使用者或界面 | 当前可用功能 | 边界 |
| --- | --- | --- |
| Staff 账号 | 输入采购、查看自己的采购及单据照片 | 无法进入管理后台、查看其他员工采购或管理账号 |
| Manager 账号 | 查看所有采购、报表、供应商汇总、管理员工及查看登录记录 | 员工管理功能不用于修改经理本人或其他经理账号 |
| Staff workspace | Add purchase、My purchases | 经理进入此界面时，My purchases 也只显示经理自己输入的采购；界面没有返回管理后台的按钮 |
| Management workspace | Dashboard、Purchases、Monthly reports、Suppliers、Staff accounts、Login history | 需要有效的 Manager 账号 |
| Inactive 账号 | 可能仍能完成身份认证 | 无权读取餐厅资料；停用不等于删除历史采购 |

入口：

- 员工：https://stocklog.online/#/staff/add
- 管理：https://stocklog.online/#/management/dashboard

同一个浏览器中的多个标签页会共享登录状态。切换网址不会把 Manager 账号变成 Staff 账号；员工应使用管理者分配的个人账号。

## 三、采购流程与资料

1. 员工登录并打开 Add purchase。
2. 输入采购日期、供应商，以及 1–100 行物品。
3. 每行输入物品名称、数量、单位及该行总金额；系统计算单价与整笔采购合计。
4. 可选填单据编号、备注，并附上一张单据照片。
5. 点击 Save purchase，确认保存后查看 My purchases。
6. 管理者在 Purchases 查看资料，在 Monthly reports 汇总采购。

一笔采购只关联一个供应商，但可以包含多个物品。照片是参考凭证，不会自动识别文字、填写物品或金额。备注会保存，但当前采购查询视图没有提供备注字段，因此历史详情及 Excel 不展示备注。

同一次保存遇到网络问题后重试，可避免重复创建该笔记录；但重新填写并提交同一张供应商单据，系统不会自动识别重复。单据编号是可选的，也没有唯一性限制。数据库会保存录入账号，但当前管理采购列表没有显示员工姓名或提供按录入员工筛选；Excel 也不包含录入人。

数量可以有三位小数，金额最多两位小数。kg 与 g、tin 与 carton 分别汇总；没有自动单位或包装换算。同名物品和供应商会忽略首尾空格及大小写复用目录，但不会自动识别别名、拼写错误或不同语言的同一物品。

## 四、报表与查找

| 页面 | 内容 |
| --- | --- |
| Dashboard | 所选月份采购金额、采购笔数、供应商数、物品数、近期采购及主要供应商与物品 |
| Purchases | 采购明细、物品搜索、供应商筛选、月份或 All dates、完整采购详情及照片 |
| Monthly reports | 按物品和单位汇总数量与金额，或按供应商汇总金额 |
| Suppliers | 供应商采购金额、笔数及最近采购日期，可进入采购明细 |
| Export Excel | 导出当前期间及筛选结果，包括采购明细、物品汇总和供应商汇总 |

月份以「采购日期」判断，不是录入日期。默认只查看所选月份；找不到资料时，先检查 Purchases 的月份、物品搜索、供应商筛选和 All dates，再刷新。记录一般在页面重新获得焦点或每分钟刷新时更新，不是每笔保存后立即推送到所有设备。

## 五、账号与登录记录

经理可建立员工账号、设定初始密码、停用／启用员工，以及重设员工密码。初始密码至少 12 个字符，并需符合实际认证服务的密码规则；系统不会自动发送账号邮件，也没有强制首次登录改密码。

Login history 记录成功认证及当时的餐厅访问状态，可以按月份与账号查看。它不记录密码输入错误、每次访问页面、在线状态、IP、设备或采购修改记录。旧资料不会补成完整登录历史；停用账号成功认证时可被标记为 Blocked。

## 七、当前已知限制与需要讨论的规则

已实现边界：没有网页内采购编辑／删除、作废审批、完整操作审计、离线保存、付款追踪、库存结余、自动识别单据或分店隔离。后台数据库存在受权限限制的写入能力，因此「网页没有编辑按钮」不代表底层采购数据不可修改。

命名尚未完全统一：目前域名为 stocklog.online，但网页品牌仍出现 Ledger／Restaurant Ledger。本文使用 Stocklog 指代本项目，不代表已批准改名或已更新品牌界面。

第一轮确认结果：

| 编号 | 业务规则 | 确认结果 |
| --- | --- | --- |
| Q1 | 首阶段的系统范围 | 用户同意：专注采购记录、查找与报表；实际库存、消耗与付款追踪留待后续规划 |
| Q2 | 餐厅／分店范围 | 用户确认：先保留一家店；本阶段不增加多店隔离 |
| Q3 | 已保存的采购输入错误时，如何处理 | 用户采纳建议：员工提出更正，由经理修改或作废；保留修改前后内容、操作人、时间及原因。已确认并实现代码；线上需执行数据库升级 |

已确认的更正流程示例：员工把 RM 50 输入成 RM 500 后提出更正；经理核实后修改，并留下 RM 500 → RM 50 的记录、操作人、时间和原因。登录历史与采购更正历史是不同记录，不能互相替代。

第二轮确认结果：

| 编号 | 业务规则 | 确认结果 |
| --- | --- | --- |
| Q4 | 作废采购是否进入统计 | 用户同意：保留原记录并标记作废；不计入有效采购金额、数量及报表合计；历史可查询。已实现代码，线上需升级 |
| Q5 | 每笔新采购是否必须经理审核后才进入报表 | 用户同意：保持现有的保存后即计入报表；发现错误时再更正或作废，不增加逐笔审批流程 |

Q1–Q5 均已确认，用户另已选择员工在网页内提交更正申请。以上记录不会自动改变网页、数据库权限或采购记录；具体界面与异常处理见下述规格草稿。

### 建议的后续工作顺序

1. 为已确认的采购更正、作废和操作历史编写具体规格，涵盖员工提出更正的方式、经理操作、权限及报表处理，然后实施与验证。
2. 在采购详情显示已保存的备注，并显示录入员工，方便核对和追查。
3. 改善重复单据提示及物品命名一致性，减少重复录入和报表分组错误。

这些是后续工作建议，不表示已开发、上线或已批准全部实现细节。本次交付为系统说明、统一术语及确认过的业务规则。

下一步已细化为[采购更正与作废操作规格草稿](purchase-corrections-spec.md)。网页内提交申请已确认；其他界面与边界处理均明确标为建议，不代表功能已上线。

本文根据仓库代码及已有说明整理，并区分了用户先前反馈与独立验证：用户已反馈员工资料可在后台看到、账号功能可用、域名与 HTTPS 已完成；本轮没有重新验证线上服务或真实手机。
